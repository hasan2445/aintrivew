00

System analysis

What the project is, how it runs, and where the shipped behaviour now matches what the UI claims. The gap between those two used to be where the hard questions came from; most of it is closed, and closing it is itself the best material you have.

Purpose and workflow

InterviewAI is a mock-interview simulator. A candidate signs up, uploads a resume, picks a target role and a difficulty, and is interviewed by an LLM that generates questions from the resume, asks adaptive follow-ups, evaluates each answer, and produces a scored report. A webcam proctoring layer watches for a missing face, extra people and phones. An admin user can list all users and interview rows.

End-to-end, as implemented: signup/login → upload screen (resume + role) → setup screen (difficulty) → analysis screen posts POST /api/upload-resume with resume, role and difficulty → server extracts text (client text accepted only for PDFs) → one Groq call generates 8–12 questions → session to Redis, row to Postgres → answer loop at POST /api/session/{id}/answer, each answer carrying a turn token, evaluated and either producing a follow-up or advancing the index → report at GET /api/session/{id}/comprehensive-report, served from Postgres if already generated → POST /api/session/{id}/end, which takes no body and computes the final score server-side. In parallel the browser posts a 320×240 JPEG every 3 seconds to POST /api/analyze-frame with the session id, and the server records its own verdict.

Data model, in full

users: id PK, username unique+index (64), email unique+index (320), hashed_password, is_admin, created_at.

interviews: id PK, session_id unique+index (64), user_id FK → users.id ON DELETE CASCADE NOT NULL indexed, plus resume_name, job_role, status, score, created_at, and report_data as an unbounded JSON column. One-to-many with cascade="all, delete-orphan" on the ORM side.

Schema is created with Base.metadata.create_all() at import — still no migration tool, which is a real answer you should give plainly rather than dodge. The live interview object (questions, answers, follow-ups, evaluations, turn counter, running conversation history) lives in Redis and reaches Postgres only as the final report_data blob.

Why user_id being NOT NULL matters: an interview with no owner cannot be access-checked. Making it non-nullable means an un-authorizable row cannot exist by construction, rather than relying on every insert path remembering to set it.

Where it is genuinely strong

Ownership is enforced by a single reusable dependency (get_owned_interview) returning 404 rather than 403 so IDs cannot be probed, and /analyze-frame reuses it. Every blocking model call is pushed off the event loop with run_in_threadpool. MediaPipe, which is not thread-safe, is serialised behind an explicit lock — and now runs in static mode so the lock isn't hiding a correctness bug. Resume uploads are read in 1 MB chunks and aborted at the cap, so an oversized file is never fully buffered, and are never written to disk. Errors are logged server-side and returned as generic messages. Production boot refuses to start on a weak JWT secret, on DEBUG=true, on wildcard CORS, or with Redis unreachable. The final score is computed from data the server observed, and /end has no way to accept a number.

Where it is still weak

All questions are shipped to the browser up-front, so devtools can read ahead. Prompt injection through resume text is unmitigated. Escaping is per-call-site rather than escape-by-default. There are no migrations, no CI, no container, no metrics beyond one counter. Two independent gaze algorithms (browser iris ratio, server nose ratio) can disagree and nothing reconciles them. Three docs — README.md, INTEGRATION_GUIDE.md, architecture.md — describe a design that no longer exists.

Framing that works. The strongest thing you can say about this project is not "here is my architecture". It is: "I audited it, found 24 defects including one XSS and a scoring system the browser controlled, fixed all of them, wrote the first 38 tests, and here are the five things I know are still wrong." That is a seniority signal. Volunteering a bug before the interviewer finds it converts a weakness into evidence of judgement.

02

Core questions

The eighteen questions most likely to be asked about this repository, with what the interviewer is actually testing and the evidence to cite. Generic "what is REST" material has been removed.

  • Easy01

    Give me the two-minute version of this project.

    Testing

    Whether you can compress without either drowning them in stack names or being so vague it sounds like a tutorial. Lead with the problem, then the one non-obvious design decision.

    Shape of a good answer

    Problem (adaptive spoken interview) → the split (Postgres owns identity, Redis owns the live session, the browser owns real-time UX) → the one interesting constraint (two sequential LLM calls per turn is the latency floor, which is why the provider choice is Groq) → what you'd change.

  • Med02

    Why two data stores? Which one is the source of truth?

    Testing

    Whether the split is reasoned or cargo-culted. The wrong answer is "Redis is faster".

    Answer

    Different things, not a cache. Redis holds the live session because every answer rewrites the whole blob 30–40 times a session — in Postgres that's WAL and vacuum pressure, in Redis it's a SET that expires itself. Postgres holds ownership so that authorization has something durable: if ownership lived in Redis, an expired key would make a transcript unauthorizable rather than unavailable.

    Follow-ups they will ask

    1. What if they disagree? (Postgres wins for access control and finished reports; Redis for live state.)
    2. Why are proctoring counters a separate key? (Frames every 3s vs. a read-modify-write of the session — same blob means every frame can clobber an answer.)
  • Hard03

    Walk me through a single answer submission, and tell me what it costs.

    Testing

    Whether you know your own hot path in terms of round trips, not just function names.

    Answer

    One Postgres SELECT (ownership), a rate-limit check, two Redis GETs, the turn check, one Groq call to evaluate, conditionally a second Groq call for the follow-up, one Redis SET. The two LLM calls are the latency floor and cannot be parallelised, because the follow-up prompt consumes evaluation.follow_up_direction.

    The detail worth volunteering

    It used to be three Redis GETs — the route re-read the whole session just to check whether the status had flipped to "completed", which submit_answer already knew. And the turn check sits deliberately before both LLM calls, so a duplicate submission costs one GET and a 409 rather than two Groq calls.

  • Hard04

    Two answers submitted at the same time. What happens, and why didn't you use a lock?

    Testing

    This is the concurrency question, and "I'd add a lock" is the answer that loses it. They want to hear you reject the obvious tool for a stated reason.

    Answer

    The second gets a 409. The session carries a monotonic turn; the client echoes it; a mismatch raises StaleTurnError. A lock would have to be held across two sequential Groq calls — seconds — so its TTL has to be long enough for the slow case and short enough not to wedge on a crash, and any TTL you pick can expire mid-call. A turn token has no lifetime to get wrong, and rejects the duplicate before spending the LLM calls.

    Concede this before they push

    turn is optional for backward compatibility, so omitting it restores last-write-wins. It should become required once no old clients are live. The threat model is a candidate racing themselves, not an attacker.

  • Expert05

    Who computes the final score?

    Testing

    Trust boundaries. This is the single best story in the project — do not let them find it first.

    Answer

    The server, from evaluations and server-observed frames. It used to be the browser: the results page fetched the report (which wrote the backend score) and then immediately POSTed its own number to /end, overwriting it. /end now takes no body at all.

    The line that lands

    "The endpoint validated float, ge=0, le=100. That's the part I'd point at — it looks like a security control and it's a shape check. It confirms the number is a number. Anyone could post a 100. Validation that checks shape while ignoring provenance is something I now specifically look for."

  • Expert06

    Your report showed an eye-contact score. Where did that number come from?

    Testing

    Intellectual honesty about a metric. Many candidates would bluff this.

    Answer

    Now: (frames − looking_away − no_face) / frames from the server's own counters, and None when no frames were analysed, in which case the UI omits the bar and says why. Before: avg_technical × 0.90 — a rescaling of one number, clamped to [40,95] so it always looked reasonable.

    The judgement point

    "The clamping made it worse, not better — it's what made the fake number look defensible. A number that looks measured and isn't is worse than an empty state, because the candidate acts on it. Someone practises eye contact for a week on the strength of their technical score times 0.9. 'Never show a value you can't defend' is the rule I took from this."

    Expect the follow-up: "then is the overall comparable?"

    Yes — the overall is a weighted percentage, not a mean. Fixed weights (technical .35, communication .20, confidence .15, resume alignment .15, eye contact .15); when a component can't be measured its weight is redistributed proportionally so they re-sum to 1.0. Dropping eye contact scales the other four by 1/0.85. A perfect candidate scores 100% with or without a camera — that property is the test. The response also carries score_basis naming the components used, so a missing one is visible rather than silently absorbed.

  • Hard07

    Is there an XSS in this app?

    Testing

    Whether you understand that LLM output is untrusted input.

    Answer

    There was — five sinks in interview.js, all fed by LLM output, in a file that escapes correctly a few lines away. Chained: resume text is attacker-controlled (the file and the text are independent form fields), it goes into the generation prompt, the model's output goes into primary_question, and that went into innerHTML raw — in a page whose JWT sits in localStorage.

    The part that earns respect

    "Five escapeHtml() calls is a fix, not a solution. Hand-escaping at every call site means you only need to forget once, and this codebase proves it twice in one file. The class is still open until rendering goes through a tagged template that escapes by default."

  • Med08

    How do you stop one candidate reading another's interview?

    Testing

    IDOR awareness, and whether the 404 was deliberate.

    Answer

    get_owned_interview, a dependency every session route depends on. Mismatched owner raises 404, not 403 — 403 confirms the id exists, which turns the endpoint into an enumeration oracle. user_id is nullable=False so an unowned row can't exist. The UUID is defence in depth, not the control — before this dependency it was the control, which is a textbook IDOR.

  • Hard09

    What happens if Redis goes down?

    Testing

    Whether "graceful degradation" is a reflex or a decision.

    Answer

    In dev it falls back to a process dict, so the repo runs with no Redis installed. In production it raises and the process doesn't start. It used to degrade silently everywhere: with four workers, each got its own dict, so an answer landed on a worker that had never seen the session — "Interview session has expired", mid-interview, at random. The docstring said "single-worker development only", but a docstring isn't an enforcement mechanism.

    Why this fix is satisfying

    The pattern was already in the codebase — settings.py refuses to boot on a weak JWT secret, database.py connects eagerly and dies in production. Redis was the one piece with the opposite treatment, for no reason other than nobody having looked at the three together.

  • Med10

    Explain the follow-up logic. When does a thread end?

    Testing

    Whether the state machine is designed or accreted.

    Answer

    Every primary question gets at least one follow-up, unconditionally — the first answer makes a claim, the follow-up tests whether it's real, and making that conditional on the score would give strong candidates a shallower interview. After that: continue while depth < 3, the rating is poor/fair/good, and you haven't answered "poor" twice in a row.

    The two-poor exit

    Added because only "excellent" or the cap could stop a thread before, so a candidate who plainly didn't know a topic got three consecutive probes on it. The loop now terminates on certainty in either direction. Note the counter resets on a better answer — that's the case a naive implementation gets wrong, and there's a test named for it.

  • Hard11

    How do you get reliable JSON out of a model that emits text?

    Testing

    Practical LLM engineering, and whether you know why the naive approach breaks.

    Answer

    Two layers, in one place. Strip fences, then json.JSONDecoder().raw_decode() from the first { — it parses the first complete object and reports where it stopped, so a trailing remark or a second object is fine. Then normalise every field against a whitelist: unknown category → skill, unknown difficulty → intermediate, score > 10 → divide by 10 and clamp.

    Volunteer this

    "It was first-{-to-last-}, copy-pasted into three functions. Given two objects it produces a string spanning both, which isn't valid JSON. Two of my ten parser tests fail against the old implementation. And layer 2 is the one that matters — the code has explicit handling for score: 85 and for a category called 'engineering scenario', which tells you both actually happened."

  • Expert12

    What happens when the evaluation LLM returns junk?

    Testing

    Whether your fallbacks were designed or just stopped the exception.

    Answer

    It returns a hardcoded "good" rating, tagged unscored=True, excluded from the score, and reported to the user. "Good" rather than "fair" is deliberate: the rating feeds the follow-up decision, and "fair" would escalate an LLM hiccup into three more probes on a topic the system knows nothing about.

    The honest framing

    "The original design wasn't wrong, it was incomplete. It made a real trade — distort the score rather than the flow — and then never implemented the 'distort the score' half in a way anyone could see. The 8.0 went into the average as real, and 8.0 is above the midpoint, so parse failures inflated the final number. One boolean closes it."

  • Hard13

    You run face detection in the browser and on the server. Why both?

    Testing

    Whether the duplication is reasoned. The wrong answer is "for accuracy".

    Answer

    They no longer duplicate. The browser is the sole source of face presence and gaze — it runs FaceMesh at camera rate with an iris-based estimate. The server runs only YOLO, for phone and extra-person detection, on one 320×240 JPEG every 3 seconds. Browser = measurement, server = verification. The server used to run its own FaceMesh too, computing a coarser nose-ratio gaze at 1/90th the sample rate, purely so the number would be server-attested — and nothing here relies on that attestation.

    The privacy point worth making

    "Frames are never stored. Only five integers per session. The system can say '40 of 200 frames showed the candidate looking away' without retaining a single image of them."

  • Expert14

    There's a lock around MediaPipe. What does it cost, and what did it fail to fix?

    Testing

    Whether you understand the difference between a throughput problem and a correctness one. This is the best CV answer in the project.

    Answer

    Cost: every face analysis in the process is serialised, which is a hard concurrency ceiling. What it didn't fix: the shared instance ran static_image_mode=False, telling MediaPipe to carry tracking state between frames — while being fed interleaved frames from different candidates on different webcams. The tracker was told "next frame of the same video" when it was a different person in a different room.

    The line

    "The lock looked like the fix — someone saw a concurrency problem, added a lock, the crashes stopped, and the real bug kept running underneath, now reliably. I fixed it with static_image_mode=True, then asked the better question: why is this on the server at all? The browser already did it better. The lock, the model and 121 MB of dependency are all gone."

  • Med15

    Why Groq and llama-3.3-70b?

    Testing

    Whether the model choice has a reason beyond "it was free".

    Answer

    Latency. It's a spoken interview — the candidate stops talking and waits, and every turn is two sequential calls, so per-token speed is the biggest lever on how the product feels. A stronger, slower model makes the conversation feel broken regardless of question quality. Temperature 0.2 because two of three prompts demand parseable JSON and the resume already supplies all the variation the questions need.

    Have this ready

    "timeout=60, max_retries=3 are wired in now — they were defined in config and never imported, so the client ran on library defaults and an unbounded call could pin a threadpool worker. If I were tuning it I'd split into two clients: short timeout and one retry for the interactive answer path, longer budget for generation behind the progress screen."

  • Med16

    How is this tested, and what would you write next?

    Testing

    Get ahead of it. There were zero tests until recently and AUDIT.md referenced two files that don't exist.

    Answer

    38 tests: 20 on the state machine, 8 on evaluation normalisation, 10 on JSON recovery. Two fakes, about eighty lines, no production refactor — the seams were already there (the LLM behind self.generator, the store behind RedisSessionStore, the CV models behind lazy loaders) and had never been used.

    Next, in order

    1. Route tests: the ownership 404, the 409 on a replayed turn, the 429s, and that /end refuses a body.
    2. Characterization tests for the AUDIT.md list — dozens of past fixes with nothing holding them fixed.
    3. Frontend tests with the jsdom already sitting in package.json.
  • Hard17

    How would you know any of this was failing in production?

    Testing

    Operational maturity. Don't oversell what you have.

    Answer

    /api/health reports the session-store mode and a cumulative evaluation-parse-failure counter. That's the minimum viable version and I'd describe it as such — it's an affordance for a human who already suspects something, not alerting. Nothing polls it, nothing pages.

    What's missing

    Counters on all three fallback paths, 429 rates per limiter, structured logs, and a histogram on Groq call latency — which is the metric that actually predicts whether this product feels broken.

  • Expert18

    You found 24 bugs in your own project. How?

    Testing

    Process, not luck. This question rewards a repeatable method.

    Answer — four techniques

    1. Follow values, not files. Pick a value, ask who writes it and who reads it. The difficulty picker, the client score and the proctoring counters all had a writer and no reader. You cannot find that reading a file — each file looks fine on its own.
    2. Grep every exported constant for a second occurrence. Found LLM_TIMEOUT_SECONDS, report_data and is_followup — all defined, none read.
    3. Ask "what does this fallback cost?" at every except. Every silent fallback here was defensible as flow control and undefended as a data decision.
    4. Write the test before believing the bug. Two things I was sure were bugs turned out to be fine.

    The summarising line

    "The single most useful question was what would make this number wrong, and would anyone notice? Every scoring bug answers yes to the first and no to the second. That's the profile of the bugs that survive longest — not the ones that crash, the ones that produce a plausible number."

03

Interview traps

Places where a confident-sounding answer is wrong, or where the UI still names something the code doesn't do. Each of these is findable in the repo in under ten minutes.

Trap"RAG Evaluator Agent Logs"

The interview sidebar has a panel with that name, badged "Llama 3 (Groq)". There is no retrieval anywhere — no vector store, no embeddings, no document index. Evaluation is a single stateless prompt containing only the question and the answer. If you say "RAG" out loud and can't produce a retriever, you have handed them the interview.

  • frontend/pages/interview.js · _ragEvaluatorPanel

Say: "That panel is misnamed and it's on my list. It's a plain evaluation prompt with no retrieval step. If I wanted the name to be true, the retrieval worth adding is over the candidate's own resume — pull the relevant experience section and put it in the evaluation prompt, so 'you said you used Kafka' can be checked against what the resume claims."

Trap"Running Agent Tasks" — five agents

state.agentStatus is a plain object whose strings are assigned by hand around API calls. There is no agent framework, no scheduler, no tool loop, no autonomy. It is a progress indicator with an ambitious label.

  • frontend/js/state.js · agentStatus

Say: "It's a status display, not an agent system. I'd rename it. What it does represent honestly is the pipeline stages — generate, evaluate, follow up — which are real, sequential, and not agentic."

TrapThe camera overlay when there's no webcam

startCvCanvas() draws a synthetic bounding box with random keypoints and a hard-coded confidence figure. It renders as though it were tracking. If an interviewer denies camera access and sees "FACE TRACKED", that is a credibility problem, not a UI bug.

  • frontend/pages/interview.js · startCvCanvas

Say: "That's a demo placeholder for screenshots and it should be labelled as one. Same lesson as the eye-contact score — don't render a value that implies a measurement you didn't take."

TrapThe README describes a different project

README.md lists OpenAI, Gemini and langchain-google-genai as the NLP stack. None are imported; the only LLM is Groq. INTEGRATION_GUIDE.md documents a flat file layout (services.py, models.py at the root) from before the package refactor. architecture.md describes "4 questions per skill", the deleted bank-based design.

Say: "Those are stale and I know it. The unused OpenAI config in core/config.py is deleted; the docs are the last thing on the list, deliberately — I'd rather rewrite them after the code stops moving than write them twice."

Trap"Your proctoring is server-side now, so it's tamper-proof"

Don't claim this. A client can still simply stop sending frames. What changed is that the policy is no longer client-controlled — you can't decide what a phone is worth, or post a 100.

Say: "Going quiet is handled. Answer timestamps are server-stamped, so the interview's duration can't be forged, and frames arrive every 3s — so the server knows how many should have come. If the feed worked and then stopped, attentiveness is scored over the expected frames, not the received ones, so unaccounted time counts against you. Zero frames is treated differently and never penalised: that's someone with no webcam, and they claimed nothing. The property I'd point at is that going dark now scores worse than being caught with a phone — before, suppressing the metric handed its weight back, so evasion paid."

Trap"Why not use structured output instead of your JSON parser?"

This is the right answer and you should agree immediately rather than defend the parser. The trap is agreeing too far.

Say: "Agreed — Groq supports JSON mode and binding a pydantic schema removes most of this. What I would not drop is the normalisation layer: schema-valid isn't semantically valid, and 'the model returned a category we've never heard of' is a schema-valid response."

Trap"You ship all the questions to the browser"

True, and deliberate. Don't pretend it's a bug or that you missed it.

Say: "Deliberate trade. It means the interview screen never blocks on 'fetch next question' — the only per-turn round trip is the submission, which has to happen anyway. The cost is devtools can read ahead. For a self-practice tool that's fine; for a proctored assessment it isn't, and the fix is one question at a time, paying a round trip I chose not to pay."

Trap"There's an AUDIT.md full of vulnerabilities. Where did it come from?"

An integrity question, not a technical one. Answer it directly.

Study before you go

Ten things worth being able to say without reaching. Everything else you can reason about live.

  1. The exact cost of one answer submission. One Postgres SELECT, two Redis GETs, one SET, up to two sequential Groq calls — and why the two calls can't be parallelised (the follow-up prompt consumes the evaluation's output).
  2. Why a turn token and not a lock. The critical section spans two LLM calls; any lock TTL can expire mid-call. This is the concurrency answer and it must be fluent.
  3. Why 404 and not 403 on the ownership check. 403 confirms the id exists, turning the endpoint into an enumeration oracle.
  4. The scoring trust boundary, start to finish. The browser used to compute and POST the final score; ge=0, le=100 validated shape while ignoring provenance. Now /end takes no body, and the overall is a weighted percentage over the criteria that were actually measured.
  5. Why server-side MediaPipe was removed. The browser already computed a better gaze estimate (iris vs. nose-in-bbox) at 90× the sample rate. The server's only advantage was attestation, which nothing here relies on. Sourcing decides role: browser-measured means feedback, server-measured means it can carry a penalty.
  6. What unscored does and why the rating stayed "good". The rating feeds the follow-up decision; "fair" would over-probe. The flag removes the scoring consequence without changing the flow decision.
  7. Why the report is served from Postgres. Fixes the 6-hour TTL cliff and stops re-billing the improvement-plan LLM call on every refresh — one change, two problems.
  8. Why _fill_prompt can't be str.format. The templates embed the JSON schema the model must emit; every example brace would be read as a replacement field.
  9. The difference between the browser and server gaze algorithms. Browser: iris position between eye corners. Server: nose x normalised against the face's own bounding width — the naive version compared raw nose x against fixed thresholds and flagged anyone sitting off-centre.
  10. Your own list of what's still wrong. Five items, in priority order, with the reason for the ordering. Being asked "what would you do next" and having a ranked answer is worth more than any single fix.
